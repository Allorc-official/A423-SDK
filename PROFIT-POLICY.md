# Profit-driven settlement policy — 0.8.1

[Start here: installation, arguments and lifecycle maps](./README.md) · [All examples](./examples/README.md)

Implements the SDK portion of the supplied **A423 Profit-Driven Settlement Policy — Recommendation**. It is an opt-in off-chain negotiation policy. Existing users keep their current settlement behavior until configured. The 0.5 escrow contract, `a423.closing.v1`, signatures and cancellation receipt formats are unchanged.

## Configure the backend

```ts
import {createEscrowApplication} from '@allorc/a423-sdk/operations';

const app = createEscrowApplication({
  // Existing storage, authority, escrows, signerFor, addressFor,
  // limitsFor, approveSigning and validateArtifact callbacks...
  ...existingConfiguration,
  settlementPolicy: {
    costBasisFor: async job => workMeter.costBasisRaw(job.id),
    budgetFor: async job => (job.metadata as {budget_raw: string}).budget_raw,
    thresholds: {
      target_margin_bps: 3000, // 30% target
      min_margin_bps: 500,    // 5% minimum
      max_margin_bps: 4000,  // 40% maximum
      require_counter: true,
    },
    // Optional: consult a durable, authenticated owner-approval system.
    // Never return approval solely because an agent supplied a flag.
    approveException: async context => ownerApprovals.check(context),
    // Optional: only your explicitly authorized operator identities.
    canViewPrivate: async ({actor, job}) => operators.canInspect(actor, job.id),
  },
});
```

The cost provider returns a canonical nonnegative raw-token-unit integer string including agreed costs/expenses. The app owns token prices, currency conversion, decimals, invoices and mock meters. Budget is also a canonical raw-unit string; it is never inferred from USD or free-form text. Inputs are bounded by uint256. No mock usage or private key is generated by the policy.

### Initialization arguments (0.8.1)

Set `settlementPolicy.thresholds` before calling `createEscrowApplication`. Each instance has its own captured, immutable effective configuration, readable through `app.profit.configuration`; mutating the original options afterward does not change it. All configuration is checked before any cost lookup or chain transaction. Unknown/misspelled threshold names, invalid types and inconsistent bounds fail at startup.

| Argument | Default | Meaning |
|---|---:|---|
| `target_margin_bps` | 5000 | Desired gross margin; 3000 means 30% |
| `min_margin_bps` | 1000 | Minimum without owner exception |
| `max_margin_bps` | 5000 | Maximum permitted margin threshold |
| `require_counter` | true | Require a worker counter before accepting the requester's first offer |

Require `0 <= minimum <= target <= maximum < 10000`; 100 basis points equals 1%. Supply either `thresholds` or the existing `policy: createSettlementPolicy(...)` form, not both. Omitting both preserves the defaults. Cost and budget providers, explicit owner-approval checks, wallet signing/spending limits, network and confirmation depth remain separate initialization callbacks/settings; they are not client-controlled trade arguments.

Changing defaults does not rewrite already frozen negotiation snapshots. For new jobs, create an SDK instance with the desired configuration. Do not silently change policy thresholds during an accepted negotiation.

The defaults are 50% target gross margin, 10% minimum and 50% maximum. They are configurable SDK primitives; the app chooses its business policy. Profit is payout minus cost, and gross margin is profit divided by payout. A 50% target means twice the cost, not 1.5 times the cost.

The service freezes cost, budget, escrow total and configuration in private durable KV at the **first closing proposal attempt**, including requester proposals. Freezing before the transaction prevents retries/counters from sampling growing costs; a rejected proposal does not unfreeze it. Live worker previews before that attempt do not freeze the meter. Concurrent first attempts reuse the atomic winning snapshot. A new agreement/generation receives a new snapshot. Do not place internal costs in public metadata, claims, mail or proposal terms.

## Pure calculation

```ts
import {createSettlementPolicy} from '@allorc/a423-sdk/policy';
const policy = createSettlementPolicy();
const plan = policy.evaluate({
  cost_basis_raw: '600505',
  budget_raw: '800000',
  escrow_raw: '5000000',
  offer_raw: '800000',
  negotiation_round: 1,
});
// target_payout: 1201010; min_payout: 667228
// recommended_payout: 800000; expected_profit: 199495
// expected_margin_bps: 2493; viability: below_target
```

Amounts are raw integers. Payout thresholds use ceiling division, margins use signed floor basis points, and no floating-point token arithmetic is used. `2493` means at least 24.93%, a conservatively truncated display. `null` margin means zero payout; it is not a zero-percent profit claim. For configurable non-50% thresholds, upward rounding can exceed the requested margin by the unavoidable smallest token unit.

`target_payout`, `min_payout` and `max_payout` are theoretical thresholds; they may exceed budget/escrow. **Only `recommended_payout` is a capped proposed amount**, equal to the lesser of target, budget and escrow. A theoretical threshold larger than uint256 is still returned exactly as a string, but the recommended allocation cannot exceed its uint256 input caps.

| Condition | Behavior |
|---|---|
| Zero cost | Recommend worker 0, full payer refund |
| Affordable amount below cost | Owner approval or decline; never silently accept a loss |
| Affordable amount below minimum payout | Owner approval required |
| Budget below target but above minimum | Recommend the highest affordable payout |
| Target affordable | Recommend target; do not exploit excess budget |
| Offer above budget, escrow or maximum payout | Reject through the SDK; counter within limits |
| First requester offer | Counter before accepting when `require_counter` is enabled |

`decision` is advisory; it does not sign, broadcast, promise acceptance or automatically cancel a job. `requires_owner_approval` marks economic exceptions. Profit projection is based on the app's cost estimate, not an on-chain audit of real expenditure.

## Proposal and acceptance integration

When enabled through the factory, the same workflow preparation and authorization apply to generic HTTP actions, chat tools and direct workflow calls:

- An omitted worker `worker_amount` in `propose_settlement` / `counter_settlement` defaults to the capped recommendation. Below-minimum defaults are still blocked until approved.
- An omitted requester amount defaults to 0. The requester may propose a full refund, but cannot force the worker to accept it.
- Explicit worker proposals must satisfy minimum/cost and maximum/budget caps, or have a named owner approval for the lower bound.
- `accept_settlement`, `approve_cancellation` and `execute_cancellation` apply the policy regardless of which actor relays both signatures.
- A confirmed worker response after the first requester offer satisfies the counter requirement. The requester can accept the worker's own ask directly; the worker cannot accept a first requester offer without countering. An initial worker ask followed by the first requester counter is still a first requester offer. After negotiation, an affordable offer at or above minimum may be accepted even below target.
- Owner exceptions require a trusted server callback returning `{approved:true, approval_id:'durable-owner-decision-id'}`. The callback receives the exact action, amount, current proposal hash and evaluation. An agent's `owner_approved` flag has no effect. The approval ID is privately recorded. Recheck the callback on subsequent actions; approve only the intended amount/revision/action.
- Owner approval **cannot** override the budget, escrow or maximum payout. Arbitrator/timeout/refund exits remain available and are not obstructed by profit targets.

Keep revision/hash, signature and role validation. A policy decision cannot replace counterparty consent. The SDK does not autonomously fabricate work claims, renegotiate repeatedly or guarantee profit. Direct external contract calls are not governed by this off-chain business policy. Explicit external transaction evidence may be adopted without the economic guard, because the adapter only validates an already executed transaction and cannot broadcast through that path. Observe-only reconciliation also bypasses profit approval checks, so a withdrawn owner exception cannot hide an already executed result; fresh spending/resume still requires authorization. Actual arbitration or timeout payouts can realize a loss; projections report the actual result.

For custom workflow construction, wire `service.prepare` as `prepareInput` and compose `service.authorize` with your existing authorization. For custom signing/approval flows outside this workflow, call the same service explicitly. Merely importing `createSettlementPolicy` does not enforce it.

## Agent tools and prompts

The factory's chat tools add `list_jobs`, `reconcile_job` and `inspect_settlement_policy({job_id})`. Inspection returns a role-aware profit projection and a prompt fragment. Add that fragment to your agent's system/tool instructions. The factory does not rewrite a remote LangGraph prompt automatically.

```ts
const prompt = app.profit.prompt({role:'worker'});
// Or: settlementPolicyPrompt({role:'worker', policy, override: customPrompt})
```

The worker fragment prioritizes profit, caps, explicit loss approval, counters, confidentiality, correct job IDs and confirmed receipts. The requester fragment prioritizes completed work, budget and receipts without exposing worker economics. Quote pricing and real execution/usage metering remain application responsibilities; use the pure evaluator with estimated costs before quoting. Closing policy does not silently rewrite an already funded agreement price.

## Status, receipts and privacy

The factory supplies `profitFor` to the application handler. It adds `profit` to `/api/state` jobs and fresh JSON/PDF receipt projections, and exposes `GET /api/a423-profit/:id`. All require participant credentials. `canViewPrivate` does not grant access to an otherwise inaccessible job; an operator must already have participant access. The pure protocol job records, public event stream and on-chain receipts contain no new profit/cost fields.

- Worker and explicitly permitted operator: cost basis, target/minimum/maximum, affordability, current allocation, projected profit/margin, target status and whether the basis is frozen.
- Requester/other participants: proposed amount, confirmed actual amount and evidence status only. Internal cost, budget snapshot, profit and margins are omitted. Public reads never invoke the cost provider.
- `realized_*` fields remain null until a settlement event freshly revalidates on the configured chain. Reorged, missing or unavailable evidence does not produce realized profit. Acceptance and a cached terminal state are insufficient.
- The reference dashboard displays these role-specific fields using raw units and basis points. The application should format token decimals and distinguish simulated versus invoiced costs.

`profitProjection({evaluation,payout_raw,confirmed})` is a pure helper: its caller must prove confirmation before setting `confirmed:true`. Prefer the factory/service projector with a real evidence revalidator.

## Supported malformed-pending recovery

Use the server-side SDK API instead of mutating workflow rows with raw CAS:

```ts
const job = await app.workflow.get(jobId, workerId);
await app.workflow.rejectPendingOperation(jobId, {
  operation_id: job.pending.id,
  reason: 'Runner emitted a missing or malformed result_hash; will retry with a real artifact',
}, {actor: workerId});
```

The engine requires the current operation ID, the original operation's role/authorization, input-integrity verification and an adapter's `never_executable` proof. It atomically records a rejected operation and recovery audit event without advancing the job or moving funds. A conflicting write fails CAS.

The reference adapter supports **only a syntactically invalid `submit.result_hash`** with no external transaction reference, no journaled operation or replacement, and no on-chain submission. Such input cannot encode a valid submission transaction. Valid inputs, unknown transaction intents, RPC outages, journal entries and other actions cannot be discarded. Reconcile/resume those instead. A custom adapter's recovery hook is trusted security code and must prove the same impossibility, including concurrent execution safety; it is not an unconditional rejection callback. No recovery HTTP/chat endpoint is exposed by default.

## Application migration checklist

The remote app described in the Markdown is separate from this SDK repository. To adopt this release there:

1. Install 0.8.1 after publication; configure the factory's `settlementPolicy` callbacks against `lib/a423/work-meter.ts` and the original budget.
2. Expose `cost_basis_raw` from the simulated meter, clearly label it simulated, and let the SDK freeze the closing snapshot.
3. Remove the cost-recovery-only default from `lib/a423/chat04.ts`; omit worker amount to use the policy default, or use the evaluator explicitly. Keep work/progress claims public and costs private.
4. Inject the role-specific prompt; use inspection for private worker reasoning and list/reconcile tools for recovery.
5. Display `profit` projection fields in the dashboard and summaries. Requester views must not copy worker-private fields into mail, shared caches or logs.
6. Replace the malformed-submit raw CAS repair with `rejectPendingOperation` and preserve existing transaction journals.
7. Run the funded cancellation journey with an actual cost provider; verify target, budget-limited, loss-approval, zero-work, privacy and receipt cases.

No independent audit, external deployment, publication or remote application migration is performed by installing the package.
